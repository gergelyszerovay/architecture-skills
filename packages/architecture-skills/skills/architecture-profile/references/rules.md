# Rule vocabulary

The structural and coverage rules a profile can select, their parameters, and the tool
that implements each one. Parameters are `key=value` pairs separated by `; `, or `none`.
A value that is a list separates its items with `, `.

**Engines.** A profile row names one engine in its Enforced by column. The rules over the
repository's imports are `architecture-check`'s: the `dependencies` and `facades` rules of
`@gergelyszerovay/reviewer2-architecture-check` (`reviewer2-check`) judge them over the manifest's
symbol-level edges (below), and it is the one engine of the import rules: a project that does not
run `reviewer2-check` has none (dependency-cruiser, the fallback of plan 0121, is retired since
plan 0125). `eslint-rules.cjs` still builds the syntax rules (`no-symbol`, `providers-only`,
`entry-only`) and, for a project without `reviewer2-check`, `max-facades-per-component`. The value
`dependency-cruiser` of the Enforced by column is a value older profiles had; architecture-check
judges such a row as `architecture-check`.

### architecture-check

The `dependencies` rule of `@gergelyszerovay/reviewer2-architecture-check` (`reviewer2-check --rule dependencies`) judges the rows marked `architecture-check` (and `dependency-cruiser`, a value older profiles had) over the manifest's symbol-level edges, as a sub-check named like the row (`contract` for `contract-only`); the `facades` rule judges `max-facades-per-component`. It reads the roles, layers, blocks and parameters from the profile's rows and reports an `error`, or an `info` with the reason when the package doc's Rule Exceptions table covers the file. How it reads the rows:

| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `library-roles`          | A library the profile gives no role is an `error` at its `src/index.ts`, so its imports are never passed in silence: with `role-source=context-path` a shared library under a row without `shared-role`; with `role-source=lib-doc` a library whose lib doc is missing, does not bind to the lib template (a doc binds through a `markdown-schema-templates` link in a folder above it) or names no role.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `block-allow-list`       | Judges the block of the file that declares the imported name, through barrels, so it closes the gap `originating-declaration` records; one finding per importing file and declaring file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `contract-only`          | Judges the declaration: a library whose role is not in `index-roles` imports from a `contract-roles` library only declarations of the listed blocks, through whatever entry. With `contract=` it also judges the contract entry's contents and an import of the index. One finding per importing file and library.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `layer-packages`         | Matches the specifier (a pattern covers the package and its subpaths; `@types/<name>` covers `<name>`); built-ins are written `node:<name>`. `*` covers every external package and no package of the workspace; the `workspace` token (below) covers the workspace packages the importing package declares with `workspace:`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `no-testing-in-prod`     | A package-level `test-entry` file (`src/testing.ts`) counts as a testing file, as a library's does.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `acyclic`                | One finding per group of files that depend on each other, at its first file, naming the shortest cycle.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

An `error`; the row's `blocks` are block names (`step`), matched against the Blocks table. Who else calls a listed block stays with `block-allow-list`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `file-naming`            | Not a `dependencies` sub-check. Its first half (every source file has a block suffix) is the `suffixes` rule below; the primary-declaration naming is the `declarations` rule's warning.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `lazy-places`            | A sub-check of `dependencies` over the dynamic edges: a library a `.routes.ts` of another library loads through `import()` gets an `error` for every static import from a file of another library (an `import type` and a test file's static import included; an `import()`, in a test file too, is no static import), one per importing file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

The `suffixes` rule (`reviewer2-check --rule suffixes`) judges the part of `file-naming` and of the
block-naming decisions that no row states: in a package whose profile has `Classifier: file-suffix`, every
`.ts` file of the manifest's `source` role under the package's `libs/` or `app/` ends with the suffix of a row of
the Blocks table. Its exemptions (the library entries at the root of `src/`, `app/index.ts`, vendor roots, and what
is not a source file in `libs/` or `app/`) are listed in the architecture-check lib doc, D15. An `error` at the
file; it is not part of the gate until the packages are renamed.

## Layers

A layer's Allowed packages cell is `none`, or a list of package patterns; built-in modules are
written `node:<name>`. `*` in the list stands for every external package, and never for a
package of the repository's own workspace: another workspace package is another hexagon, so a
layer imports one only when its cell lists the token `workspace`, or when the package doc's
Approved Packages table names that package for the layer (`approved=package-doc`).
architecture-check reads `workspace` as the packages the importing package's `package.json`
declares with the `workspace:` protocol, in any dependency field, among the edges the manifest
resolves to another workspace package, so an undeclared workspace package is a finding too. A
layer for code that only wires the repository's own packages together (a Node bridge) lists
`workspace` and the few built-ins it needs; a composition layer that also takes any external
package lists `*, workspace`.

## Coverage rules

| Rule                      | Parameters                            | Checks                                                                    |
| ------------------------- | ------------------------------------- | ------------------------------------------------------------------------- |
| `export-has-spec`         | `kind=<kind>`                         | Every export of the block has a spec of that kind.                        |
| `public-method-has-spec`  | `kind=<kind>`                         | Every public method has a spec of that kind.                              |
| `failure-path-has-spec`   | `kind=<kind>`                         | The block has a spec of that kind for a failure path.                     |
| `interactive-ui-has-spec` | `kind=<kind>`                         | A UI block with local state or keyboard handling has a spec of that kind. |
| `port-has-contract`       | `suite=<suffix>; runs=fake, adapters` | Every port has a contract suite run against its fake and every adapter.   |
| `dispose-has-spec`        | `kind=<kind>`                         | The block has a spec of that kind that calls `dispose()` twice.           |

The `coverage` rule of `@gergelyszerovay/reviewer2-architecture-check` (`reviewer2-check --rule coverage`)
reads the table as data and judges every row from the manifest's specs, whatever its Enforced by cell says
(`planned` until a later plan flips them). A row with `kind=<kind>` asks for a spec of that kind in a test file
beside each file of the blocks it applies to (`x.use-case.test.ts` for `x.use-case.ts`: the manifest ties a
spec to a file only that way, so a spec in a shared test file covers nothing). The reading is per file, as the
Applies to cell says: `public-method-has-spec` asks one scenario per facade file, not one per public method, and
`interactive-ui-has-spec` one for every `.ui.ts`, interactive or not; a finer granularity needs a parameter, a
question for the Angular profile. A file that exports only types is not judged, and a `.main.ts` is judged as one
unit. `port-has-contract` asks for `<port stem><suite>` in the port's library, run by a test file of the library
(or of `app/`) that reaches both the suite and each fake (the `fake` blocks of the library that implement the
port) and each adapter (the driven-layer files of the library and the bridging-layer files anywhere that
implement it). A gap is a `warning` (an `info` in an advisory package, `"enforcement": "advisory"`); under `"coverage": "specified"` a skeleton (`it.todo` with its complete
metadata, D51) satisfies a row and is listed as an `info` (debt). The report adds the debt per package after
the count. The rows that name no kind or suite are not judged.

## Scripts

In `scripts/`, all reading the profile a package binds to:

- `load-profile.cjs`: `loadBoundProfile(packageDir)` returns the profile as data: the installed
  profile, whatever `version` the binding still names, with the binding's `coverage`,
  `enforcement` and `frozen`; `frozenLine(profile, packageDir)` is the one line the scripts print
  for a frozen package.
- `vendor-roots.cjs`: `vendorRoots(profile, packageDir)` reads the vendor roots from the package
  doc (`vendor-roots=package-doc`), each a directory and the package its imports use;
  `check-tsdoc-tags.mjs` and `check-block-placement.mjs` skip them, and a package's ESLint config
  can ignore them, so no config names a vendor path.
- `eslint-rules.cjs`: `buildRestrictedSyntax(profile, { base })` returns ESLint flat-config
  entries for the `no-symbol` rules marked `eslint`: one entry per restricted block, setting
  `no-restricted-syntax` to the package's own `base` selectors plus the block's. Pass the
  selectors the package applies everywhere as `base`, and place the entries after the
  package's general rules: a later entry replaces a rule's options instead of merging them.
  `buildMaxFacades(profile, { files, severity })` returns the entry for
  `max-facades-per-component` when it is marked `eslint` or `architecture-check` (the fallback of
  the `facades` rule, for a project without `reviewer2-check`), as a plugin rule named
  `architecture-profile/max-facades-per-component`. `buildProvidersOnly(profile, { severity })`
  returns one entry per block of `providers-only`'s `blocks` (`**/*.<block>.ts`) when it is
  marked `eslint`, as the plugin rule `architecture-profile/providers-only`, and `buildEntryOnly(profile, { severity })` returns the same for `entry-only` (`**/*.entry.ts`). The entries share
  one `architecture-profile` plugin object per profile, since ESLint refuses two objects under
  one plugin name for a file.
  `tsdocSyntaxPlugin(tsdoc)` takes no profile: given the package's `eslint-plugin-tsdoc`, it returns
  the plugin to register as `architecture-skills`, whose rule `architecture-skills/tsdoc-syntax`
  replaces `tsdoc/syntax`. It runs the same rule (the same parser, the package's `tsdoc.json`) and
  reports every message but the one on a `{@link}` whose target is a repository-root path
  (`/<path>.<extension>`, optionally `#<key>`): the row citation of the citations skill
  (**Rows**), which the TSDoc parser rejects for its leading `/`.
- `check-tsdoc-tags.mjs <package-dir>` and `check-block-placement.mjs <package-dir>`.

A package reaches the scripts by package name, never by a relative path out of its folder: it
declares the skills' package (`@gergelyszerovay/architecture-skills`, the `packages/architecture-skills/` folder) as a
devDependency (in this repository `workspace:*`), runs the checkers as the
package's bins (`check-tsdoc-tags .`, `check-block-placement .`; three-block-architecture adds
`check-names` and `check-host-tier`) and requires the modules by their short names
(`@gergelyszerovay/architecture-skills/load-profile.cjs`, `@gergelyszerovay/architecture-skills/eslint-rules.cjs`,
`@gergelyszerovay/architecture-skills/vendor-roots.cjs`); any other file of a skill is
`@gergelyszerovay/architecture-skills/skills/<skill>/<path>`.

A package states no dependency rule of its own: a rule the profile does not state is a profile
row (or an Approved Packages row, for `layer-packages`), so the one engine judges it.

An architecture skill may ship the checker of a rule in its own `scripts/` when only that
architecture uses the rule: three-block-architecture's `check-names.mjs` implements
`file-naming`, its `check-host-tier.mjs` implements `entry-excludes-package` and its `check-units.mjs`
implements `unit-manifest` (the file a unit carries, its format version and its keys, read from the row) and `unit-imports` (the scope of the imports of other kits' units and the refusal of cycles, read from the row).
A profile marks such a rule `checker`.
