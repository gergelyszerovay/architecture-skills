# Constitution: node-block-architecture

> Node.js applications built as hexagons of feature libraries, documented and tested so tools can examine code, docs and specs together.

## 1. Identity

- Kind: skill
- Applies to: Node.js/TypeScript packages that adopt the node-block-architecture skill: servers, CLIs, MCP servers, workers, serverless functions, libraries and multi-entry packages

## 2. Requirements

| ID  | Requirement                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | The application talks to the outside world only through ports, and adapters plug into those ports.                                         |
| R2  | Business logic is independent of transports, frameworks, SDKs and I/O, so the same use cases can back several entry points.                |
| R3  | Cohesive capabilities are features, each a small hexagon with public contracts, and no feature reaches past another's contracts.           |
| R4  | Every record and every piece of in-process state has exactly one owner.                                                                    |
| R5  | Wire, row, SDK and transport types don't cross the hexagon boundary, and contracts that leave the process evolve compatibly.               |
| R6  | Lifetime, cleanup, concurrency, transaction and failure behaviour of operations and process resources are explicit.                        |
| R7  | The architecture works with the project's runtime setup, framework host and transports.                                                    |
| R8  | Every rule is enforceable by a tool or verifiable by a test or review, and known coverage gaps are stated rather than claimed as covered.  |
| R9  | Agents can apply it predictably: rules are unambiguous, every open choice has a default, and detail is loaded only when a task needs it.   |
| R10 | Documentation never repeats what the code already states; every fact has exactly one home.                                                 |
| R11 | Behaviour is specified by tests, which serve as documentation, and specs can be written before the code.                                   |
| R12 | Documentation is built on layered-docs and markdown-schema, so tools can read it as typed data and review it together with code and specs. |
| R13 | Adoption is incremental: following the architecture never requires unrelated migrations, scaffolding or new dependencies.                  |

## 3. Non-goals

| ID  | Non-goal                                                                                                                                        |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | Not a file/declaration policy; that belongs to the source-organization skill, whose barrel layout this skill extends with hexagon folders.      |
| N2  | Not a mandated framework, DI container or library stack; the default stack applies only where the project has no equivalent.                    |
| N3  | Not a feature per entity, endpoint or command, and not empty features or shared libraries created in anticipation.                              |
| N4  | Not an event-driven architecture; events are optional facts, not a mandatory bus.                                                               |
| N5  | Not a distributed-system design; deployment topology and cross-service consistency are out of scope beyond transaction boundaries and outboxes. |
| N6  | Not product documentation; product briefs, domain models, permission matrices, use cases and journeys belong to the product profile.            |
