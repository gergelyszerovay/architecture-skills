# Constitution: product-profile

> A product's intent, vocabulary, permissions, places and use cases written once at the group level, and proved by end-to-end journeys that tools can trace back to them.

## 1. Identity

- Kind: skill
- Applies to: groups of packages that form one product, their group-level layered-docs tree and their end-to-end test package

## 2. Requirements

| ID  | Requirement                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | A product's intent (who it serves, which outcomes it pursues, what it deliberately doesn't do) is written down once, at the group level.   |
| R2  | The product's vocabulary (its objects, their relationships and its roles) is shared by the docs, the code, the tests and the UI.           |
| R3  | Who may do what is explicit, and each permission states where it is enforced.                                                              |
| R4  | Every user goal is traceable from its use case to the journey that proves it, and from there to the places and libraries it touches.       |
| R5  | End-to-end tests cover only what needs the integrated system, and each one starts from a known, isolated state.                            |
| R6  | End-to-end tests read as the product's behaviour documentation: literal Given, When and Then steps in the product's vocabulary.            |
| R7  | Documentation never repeats what code or tests already state; every fact has exactly one home.                                             |
| R8  | Documentation is built on layered-docs and markdown-schema, so tools can read it as typed data and review it together with code and specs. |
| R9  | Every rule is enforceable by a tool or verifiable by review, and known coverage gaps are stated rather than claimed as covered.            |
| R10 | Adoption is incremental: a product writes only the documents it needs.                                                                     |

## 3. Non-goals

| ID  | Non-goal                                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------------- |
| N1  | Not project management: roadmaps, priorities, estimates and delivery status live elsewhere.                             |
| N2  | Not package architecture; the inside of each package belongs to its architecture skill (Angular, Node, Supabase).       |
| N3  | Not visual design; wireframes and design systems are referenced, not drawn or specified here.                           |
| N4  | Not a per-screen requirements specification; behaviour lives in specs, and the steps of a use case live in its journey. |
| N5  | Not market research or a business plan.                                                                                 |
