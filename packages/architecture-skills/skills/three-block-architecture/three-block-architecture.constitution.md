# Constitution: three-block-architecture

> three.js and shader code built as framework-independent packages of suffix-named blocks, hosted through plain data and documented and tested so tools can examine code, docs and specs together.

## 1. Identity

- Kind: skill
- Applies to: TypeScript packages of three.js and shader code that adopt the three-block-architecture skill: effects, games, kits of materials, passes and prefabs, and engines that compose other packages' kits
- Version: 0.1.0

## 2. Requirements

| ID  | Requirement                                                                                                                                                 |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | three.js code lives in a package that depends on no UI framework, and a host talks to it through plain data: no three.js object crosses the boundary.       |
| R2  | Domain logic (parameters, rules, timelines, game rules, save formats) imports nothing, not even three.js, so it is testable in Node and serialisable.       |
| R3  | Every GPU resource, listener, loop and render target has exactly one declared owner and one declared disposer.                                              |
| R4  | Reusable rendering pieces (shaders, materials, passes, effects, prefabs, props, surfaces) never depend on the runtime, so other three.js apps can use them. |
| R5  | Each file is named by its primary declaration and its block suffix, and each suffix has one responsibility.                                                 |
| R6  | Rendering backend and colour space are explicit for every rendering block.                                                                                  |
| R7  | Kits of different packages compose at defined joints without knowing each other.                                                                            |
| R8  | Every rule is enforceable by a tool or verifiable by a test or review, and known coverage gaps are stated rather than claimed as covered.                   |
| R9  | Agents can apply it predictably: rules are unambiguous, every open choice has a default, and detail is loaded only when a task needs it.                    |
| R10 | Documentation never repeats what the code already states; every fact has exactly one home.                                                                  |
| R11 | Behaviour is specified by tests, which serve as documentation, and specs can be written before the code.                                                    |
| R12 | Documentation is built on layered-docs and markdown-schema, so tools can read it as typed data and review it together with code and specs.                  |
| R13 | Adoption is incremental: following the architecture never requires unrelated migrations, scaffolding or new dependencies.                                   |

## 3. Non-goals

| ID  | Non-goal                                                                                                                                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | Not a host protocol: which parameters, events, commands or readouts a host sees, and their types, belong to the product that defines them.                                                                                                                                                                                                                                                                      |
| N2  | Not a layout or declaration policy; that belongs to the source-organization skill, whose barrel layout this skill uses.                                                                                                                                                                                                                                                                                         |
| N3  | Not a runtime or engine library: the skill ships no code to import.                                                                                                                                                                                                                                                                                                                                             |
| N4  | Not product documentation; briefs, use cases and journeys belong to the product profile.                                                                                                                                                                                                                                                                                                                        |
| N5  | Not a requirement of WebGL or WebGPU: a package picks its backend and states it. The default, the template and the examples are `WebGPURenderer` with TSL, and a decision that holds only for `WebGLRenderer` says so in its text.                                                                                                                                                                              |
| N6  | Not an asset pipeline in the skill: the skill ships no code that compresses, bakes or stores assets, and large-file storage and CDNs are out of scope; it states where a package keeps its authored assets, describes its assets in a recipe, bakes the ones its kit generates with `.exporter.ts` blocks and ships the build output (D7, D67, D68). The pipeline is a tool of the product that uses the skill. |
