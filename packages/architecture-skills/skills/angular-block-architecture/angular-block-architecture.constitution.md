# Constitution: angular-block-architecture

> Angular capability libraries with a view-model seam and a framework boundary, documented and tested so tools can examine code, docs and specs together.

## 1. Identity

- Kind: skill
- Applies to: Angular packages that adopt the angular-block-architecture skill, in any of the three source layouts

## 2. Requirements

| ID  | Requirement                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | Cohesive capabilities are encapsulated in libraries with public contracts and private interiors, whether or not they have routes or several consumers. |
| R2  | Every authoritative state value has exactly one owner, and views derive from it instead of synchronizing copies.                                       |
| R3  | Presentation is separated from application state and operations by a view-model seam.                                                                  |
| R4  | Domain logic stays free of framework, transport and presentation dependencies.                                                                         |
| R5  | External wire contracts don't leak beyond data access.                                                                                                 |
| R6  | Ownership, lifetime, cleanup, concurrency, failure and result publication of stateful and asynchronous behaviour are explicit.                         |
| R7  | The architecture works with any supported source layout and with the project's installed Angular version and vendors.                                  |
| R8  | Every rule is enforceable by a tool or verifiable by a test or review, and known coverage gaps are stated rather than claimed as covered.              |
| R9  | Agents can apply it predictably: rules are unambiguous, every open choice has a default, and detail is loaded only when a task needs it.               |
| R10 | Documentation never repeats what the code already states; every fact has exactly one home.                                                             |
| R11 | Behaviour is specified by tests, which serve as documentation, and specs can be written before the code.                                               |
| R12 | Documentation is built on layered-docs and markdown-schema, so tools can read it as typed data and review it together with code and specs.             |
| R13 | Adoption is incremental: following the architecture never requires unrelated migrations, scaffolding or new dependencies.                              |

## 3. Non-goals

| ID  | Non-goal                                                                                                                             |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ |
| N1  | Not a directory layout or file/declaration policy; those belong to the source-organization skill.                                    |
| N2  | Not a mandated state library or vendor stack; plain signal services and the project's existing store library are both valid.         |
| N3  | Not a library per component or endpoint, and not empty libraries created in anticipation.                                            |
| N4  | Not an event-bus architecture; events are optional facts, not a mandatory global bus.                                                |
| N5  | Not authorization; client policies govern UX, and the backend or database stays authoritative.                                       |
| N6  | Not product documentation; product briefs, domain models, permission matrices, use cases and journeys belong to the product profile. |
